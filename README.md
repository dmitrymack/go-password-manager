# GophKeeper

Клиент-серверный менеджер паролей. Сервер хранит секреты пользователей в зашифрованном виде,
клиент (CLI) синхронизирует их между устройствами одного пользователя и умеет читать
данные без сети.

Типы секретов:

| Тип      | Что хранится                       | Команда                |
|----------|------------------------------------|------------------------|
| `login`  | логин и пароль                     | `gophkeeper add login` |
| `card`   | номер, держатель, срок, CVV        | `gophkeeper add card`  |
| `text`   | произвольный текст                 | `gophkeeper add text`  |
| `binary` | любой файл до 10 МБ                | `gophkeeper add binary`|

К любому секрету можно добавить метаданные `key=value` (сайт, банк, заметка и т.п.).

## Быстрый старт

Нужны Go 1.26+, Docker с Compose и `openssl`.

```sh
make certs                 # dev CA и сертификат сервера в certs/
cp .env.example .env       # затем заменить JWT_SECRET и MASTER_KEY:
                           #   openssl rand -hex 32
make up                    # PostgreSQL + сервер в Docker (gRPC на localhost:3200, TLS)
make client                # клиент: bin/gophkeeper
```

Клиенту нужен CA-сертификат, чтобы проверить сервер. Удобнее один раз задать переменную:

```sh
export GOPHKEEPER_CA_CERT=certs/ca.crt

./bin/gophkeeper version
./bin/gophkeeper register alice          # пароль спросит дважды, скрытым вводом
./bin/gophkeeper add login github --login alice --meta site=github.com
./bin/gophkeeper list
./bin/gophkeeper get github
```

Остановить: `make down` (данные БД остаются в volume `pgdata`).

> После изменений в коде сервера запускайте `make up` снова: он пересобирает образ.

### Сервер без Docker

PostgreSQL можно оставить в Docker (`docker compose up -d postgres`, порт `5433`),
а сервер запустить локально — он сам прочитает `.env`:

```sh
make server
./bin/gophkeeper-server            # -h — список флагов
```

Миграции применяются автоматически при старте сервера.

## Команды клиента

```
gophkeeper register <login>          создать аккаунт и войти
gophkeeper login <login>             войти (на новом устройстве)
gophkeeper logout                    удалить сессию и локальный кэш
gophkeeper sync                      скачать изменения с сервера
gophkeeper list                      список секретов (работает офлайн)
gophkeeper get <имя|id> [--out FILE] показать секрет или сохранить данные в файл (работает офлайн)
gophkeeper add login  <имя> --login L                    пароль спросит скрытым вводом
gophkeeper add card   <имя> --number N --expiry MM/YY [--holder H]   CVV спросит
gophkeeper add text   <имя> --text T | --file F
gophkeeper add binary <имя> --file F
gophkeeper edit <имя|id> [--name] [--meta k=v] [--login] [--password] [--number] [--holder]
                         [--expiry] [--cvv] [--text] [--file]
gophkeeper delete <имя|id>
gophkeeper version                   версия, дата сборки, коммит
```

- У всех `add` есть `--meta key=value`, флаг можно повторять.
- `edit` меняет только то, что передано. `--meta key=` удаляет ключ. `--password` и `--cvv`
  просят новое значение скрытым вводом.
- Флаг, который не подходит к типу секрета (например `--number` для логина), — ошибка.
- Номер карты проверяется алгоритмом Луна, срок — формат `MM/YY`, CVV — 3–4 цифры.
- `get` бинарного секрета не печатает данные, а подсказывает `--out FILE`.
- Если имя неоднозначно (два секрета с одинаковым именем), используйте ID из `list`.

Глобальные флаги (у каждого есть переменная окружения):

| Флаг          | Переменная            | По умолчанию                  |
|---------------|-----------------------|-------------------------------|
| `--server`    | `GOPHKEEPER_SERVER`   | `localhost:3200`              |
| `--ca-cert`   | `GOPHKEEPER_CA_CERT`  | системные CA                  |
| `--data-dir`  | `GOPHKEEPER_DATA_DIR` | `~/.config/gophkeeper`        |

### Офлайн-режим

`list` и `get` сначала пытаются синхронизироваться. Если сервер недоступен, печатается
предупреждение и показываются данные из локального кэша:

```
Warning: server unavailable, showing cached data (read-only mode)
```

`add`, `edit`, `delete` без сервера завершаются ошибкой
`server unavailable: read-only mode, changes are not possible` — офлайн только чтение.

## Сценарий ручной проверки

Два «устройства» моделируются двумя каталогами `--data-dir`.

```sh
export GOPHKEEPER_CA_CERT=certs/ca.crt
A="./bin/gophkeeper --data-dir /tmp/gk-a"
B="./bin/gophkeeper --data-dir /tmp/gk-b"

# 1. Регистрация и данные всех типов на устройстве A
$A register demo                                    # пароль, например Passw0rd1
$A add login github --login alice --meta site=github.com
$A add card visa --number "4111 1111 1111 1111" --holder "ALICE SMITH" --expiry 12/29
$A add text note --text "hello"
$A add binary photo --file ./some.jpg
$A add card bad --number 4111111111111112 --expiry 12/29   # ошибка: не проходит Луна
$A list

# 2. Вход на устройстве B — секреты подтягиваются
$B login demo
$B list
$B get visa

# 3. Изменение на B видно на A
$B edit github --meta env=work --password
$A sync
$A get github

# 4. Бинарные данные сохраняются байт в байт
$A get photo --out /tmp/photo-copy.jpg && cmp ./some.jpg /tmp/photo-copy.jpg

# 5. Удаление синхронизируется
$A delete note
$B sync && $B list

# 6. Офлайн: чтение из кэша, запись запрещена
docker compose stop server
$A list                # предупреждение + данные
$A get github          # работает
$A add text x --text y # ошибка read-only, код выхода 1
docker compose start server

# 7. Данные на сервере и в кэше зашифрованы
docker compose exec postgres psql -U gophkeeper -c "SELECT name, kek_version, left(encode(ciphertext,'hex'),32) FROM secrets"
strings /tmp/gk-a/cache.db | grep hunter2  # ничего не находит

# 8. Выход удаляет сессию и кэш
$A logout && ls /tmp/gk-a
```

## Конфигурация

Приоритет: флаг командной строки → переменная окружения → значение по умолчанию.
Файл `.env` в текущем каталоге подхватывается автоматически (уже заданные переменные
окружения не перезаписываются). Пример — `.env.example`.

| Переменная     | Флаг          | Описание                                              |
|----------------|---------------|-------------------------------------------------------|
| `GRPC_ADDRESS` | `-a`          | адрес gRPC, по умолчанию `localhost:3200`             |
| `DATABASE_DSN` | `-d`          | DSN PostgreSQL (обязательно)                          |
| `JWT_SECRET`   | `-jwt-secret` | секрет подписи токенов, не короче 32 символов         |
| `MASTER_KEY`   | —             | мастер-ключ, 64 hex-символа; **только из окружения**  |
| `TOKEN_TTL`    | `-token-ttl`  | срок жизни токена, по умолчанию `24h`                 |
| `TLS_CERT`     | `-tls-cert`   | сертификат сервера (PEM, обязательно)                 |
| `TLS_KEY`      | `-tls-key`    | ключ сертификата (PEM, обязательно)                   |
| `LOG_LEVEL`    | `-log-level`  | `debug`, `info`, `warn`, `error`                      |

TLS обязателен и на сервере, и в клиенте: режима без шифрования нет. Для локального запуска
хватает самоподписанных сертификатов из `make certs`.

Логи: успешные вызовы — `info`, ошибки сервера (`Internal`, `Unknown`, `DataLoss`) — `error`,
ошибки клиента (`NotFound`, `InvalidArgument`, `Unauthenticated` и т.п.) — только `debug`.

Для Docker-окружения дополнительно: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`,
`POSTGRES_PORT` (порт БД на хосте, по умолчанию `5433`). Внутри контейнера
`docker-compose.yml` подменяет хост в DSN и пути к сертификатам.

> **Потеря `MASTER_KEY` означает потерю всех секретов**: им зашифрованы все KEK.

## Разработка: тесты, линтер, сборка

| Команда           | Что делает                                                     |
|-------------------|----------------------------------------------------------------|
| `make test`       | `go test -race ./...`                                          |
| `make cover`      | тесты с покрытием, итог без сгенерированного `.pb.go`          |
| `make lint`       | golangci-lint v2.14.0 (ставится через `go run`, без установки) |
| `make build`      | сервер и клиент в `bin/`                                       |
| `make client-all` | клиент под linux/windows/darwin, amd64/arm64                   |
| `make proto`      | перегенерировать gRPC-код (нужны `protoc` и плагины)           |
| `make certs`      | dev-сертификаты                                                |
| `make up`/`down`  | поднять/остановить Docker-окружение                            |

Тесты хранилища работают с настоящим PostgreSQL. Без `TEST_DATABASE_DSN` они пропускаются,
остальные тесты от БД не зависят. Чтобы их включить:

```sh
docker compose exec postgres createdb -U gophkeeper gophkeeper_test
# в .env уже есть TEST_DATABASE_DSN=...localhost:5433/gophkeeper_test
make cover
```

`make` экспортирует `TEST_DATABASE_DSN` из `.env`; при запуске `go test` напрямую
переменную нужно задать самому. Тесты очищают таблицы, поэтому нужна отдельная база.

Версия и дата сборки вшиваются через `-ldflags` (`internal/buildinfo`), их показывает
`gophkeeper version`.

CI (`.github/workflows/ci.yml`): линтер, тесты с PostgreSQL и покрытием, statictest
Практикума, кросс-сборка клиента.

## Ротация ключей шифрования

```sh
docker compose stop server
docker compose run --rm server rotate-kek    # или локально: ./bin/gophkeeper-server rotate-kek
docker compose start server
```

Команда создаёт новый KEK и перешифровывает им DEK всех секретов. Сами данные не
перешифровываются, клиенты ничего не замечают (версии и ревизии секретов не меняются).
Прерванную ротацию можно просто запустить ещё раз. Старые KEK остаются в БД.

Сервер нужно остановить на время ротации и перезапустить после: работающий сервер загрузил
ключи при старте и не знает о новом KEK.

## Архитектура

```
cmd/server                  точка входа сервера (+ подкоманда rotate-kek)
cmd/client                  точка входа CLI
api/proto                   gRPC-протокол: AuthService, SecretService
migrations                  SQL-миграции (встроены в бинарник)
internal/aead               AES-256-GCM: общий для сервера и клиента
internal/buildinfo          версия и дата сборки
internal/testcerts          TLS-сертификаты для тестов
internal/server/
  config                    флаги и переменные окружения
  app                       gRPC-сервер, TLS, graceful shutdown
  interceptor               логирование, проверка JWT
  grpcapi                   gRPC-обработчики, ошибки → коды gRPC
  auth                      регистрация, вход (bcrypt), JWT
  secrets                   бизнес-логика секретов, валидация
  encryption                envelope encryption, ротация KEK
  storage                   PostgreSQL (pgx)
internal/client/
  cli                       команды cobra
  api                       gRPC-клиент
  session                   сохранённая сессия (токен, ключ кэша)
  cache                     локальный кэш на SQLite, данные зашифрованы
  syncer                    синхронизация кэша с сервером
  payload                   форматы данных по типам, проверка карты
  secret                    модель секрета на клиенте
```

### Протокол

gRPC поверх TLS, описание — `api/proto/gophkeeper.proto` (edition 2023, Go Opaque API). Все методы, кроме
`AuthService/Register` и `AuthService/Login`, требуют заголовок
`authorization: Bearer <JWT>`.

| Метод                  | Что делает                                                   |
|------------------------|--------------------------------------------------------------|
| `Register`, `Login`    | логин и пароль → JWT                                         |
| `Create`               | новый секрет; ID (UUID) выбирает клиент, повтор → `AlreadyExists` |
| `Update`               | замена секрета, если его `version` не изменилась, иначе `Aborted` |
| `Delete`               | удаление (остаётся «надгробие» для синхронизации)            |
| `Get`                  | секрет с данными                                             |
| `Sync(since_revision)` | метаданные секретов, изменённых после ревизии, и текущая ревизия |

### Синхронизация

У каждого пользователя есть счётчик `revision`. Любая запись увеличивает его в той же
транзакции и проставляет новое значение секрету. Клиент помнит последнюю полученную
ревизию и спрашивает только изменения после неё. `Sync` возвращает метаданные без данных,
сами данные клиент докачивает через `Get` по одному секрету — так большой файл не упирается
в лимит размера gRPC-сообщения. Удалённые секреты приходят как `deleted=true`.

Идемпотентность создания: клиент генерирует UUID секрета до отправки `Create` и при
недоступности сервера повторяет запрос (политика ретраев gRPC). Если первая попытка уже
дошла, повтор упирается в первичный ключ и получает `AlreadyExists`, что клиент считает
успехом — дубликата не будет.

Конфликты: `Update` передаёт версию, которую клиент видел. Если секрет успели изменить
с другого устройства, сервер отвечает `Aborted`, клиент просит повторить команду. Перед
каждой записью клиент синхронизируется, поэтому повтор работает с актуальной версией.

### Шифрование

На сервере — envelope encryption:

```
MASTER_KEY (env)  →  шифрует KEK (таблица keks, версии)
KEK               →  шифрует DEK (свой у каждого секрета)
DEK               →  шифрует данные секрета (AES-256-GCM)
```

Шифротекст привязан к владельцу через AAD `userID/secretID`: подменить данные одного
пользователя данными другого в БД нельзя незаметно. Пароли пользователей — bcrypt.

На клиенте данные в кэше шифруются случайным ключом, который создаётся при входе и
хранится в файле сессии (права `0600`).

## Ограничения и компромиссы

- **Шифрование на сервере, а не end-to-end.** Сервер видит данные в момент записи и чтения.
  Защищены данные в БД и её бэкапах. E2E потребовал бы выводить ключ из пароля и
  усложнил бы смену пароля и синхронизацию.
- **Метаданные и имена не шифруются** — чтобы `list` и `Sync` работали без расшифровки.
  Секреты в метаданные класть не стоит.
- **Ключ локального кэша лежит рядом с ним** (в файле сессии). Это защищает от
  случайного копирования `cache.db`, но не от злоумышленника с доступом к домашнему
  каталогу. Альтернатива — keyring ОС или ключ из пароля.
- **Офлайн — только чтение.** Офлайн-запись потребовала бы очереди изменений и
  разрешения конфликтов при слиянии.
- **Нет обновления токена.** По истечении `TOKEN_TTL` нужно выполнить `login` снова.
- **Размер данных — до 10 МБ** на секрет; файл передаётся одним сообщением, без стриминга.
- **Ротация KEK** — при остановленном сервере; ротация мастер-ключа не реализована.
- **Dev-сертификаты** из `make certs` — только для локальной разработки.
